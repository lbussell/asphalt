Imtui architecture walkthrough

Stateful immediate-mode widgets

The new design keeps the user experience familiar to Dear ImGui users while moving behavior out of extension-method bodies. Public widget calls stay terse, but each call is backed by an internal widget descriptor submitted through ImtuiContext.

Public API

context.Button("OK"), context.Checkbox(...), and context.TextField(...) remain extension methods.

Internal model

Extension methods construct internal widgets such as ButtonWidget and submit them to the context.

Persistent state

Widgets use stable WidgetID values and WidgetStateStorage for frame-to-frame state.

Testable input

Applications provide ImtuiInput to NewFrame; widget code does not read from Console.

Why the model changed

The previous widget approach implemented widgets directly in extension methods. That was fine for simple drawing helpers like boxes, but it did not scale to interactive controls that need stable IDs, focus, input handling, return values, and persistent per-widget state.

The replacement separates the friendly immediate-mode API from the widget implementation. The result is still easy to call, but the implementation is now small, composable, and directly testable.

Removed: Box/NineBox widgets Added: Text Added: Button Added: Checkbox Added: TextField

Layered architecture

Application starts a frame

The app calls imtui.NewFrame(size, input). The context rolls the current screen into the previous screen, creates a fresh screen, resets the widget cursor and ID stack, stores frame input, and starts focus processing.

User code calls extension methods

Calls such as imtui.Checkbox("Enabled", ref enabled) provide a Dear ImGui-like surface. These methods validate arguments and immediately delegate to internal widget descriptors.

Context submits internal widgets

ImtuiContext.Submit executes an IWidget or IWidget<TResult>. This keeps public adapters thin and gives widget behavior a common testable entry point.

Widgets resolve IDs, state, focus, input, and rendering

Interactive widgets call GetId, register focus, inspect CurrentInput, update state when needed, write cells with WriteText, and return immediate-mode results to the caller.

Application renders the frame

RenderFrame diffs the previous and current screens and returns ANSI output for the terminal.

Public API and backing implementation

What callers write

imtui.NewFrame(input: input);

imtui.Text("Settings");
bool changed = imtui.Checkbox("Enabled", ref enabled);
bool renamed = imtui.TextField("Name", ref name);

if (imtui.Button("Quit"))
{
    return;
}

Console.Write(imtui.RenderFrame());

What the adapter does

public bool Button(string label)
{
    ArgumentNullException.ThrowIfNull(label);

    return context.Submit(new ButtonWidget(label));
}

The extension method owns the user-facing shape. The internal widget owns behavior.

Core responsibilities

Component Role Important APIs
ImtuiContext Owns screens, IDs, widget state, input, focus, widget submission, and rendering. NewFrame, GetId, GetWidgetState, Submit, WriteText, RenderFrame
WidgetExtensions Provides the public immediate-mode API and delegates to internal descriptors. Text, Button, Checkbox, TextField
IWidget / IWidget<T> Defines the minimal internal contract for widgets that execute against a context. Execute(ImtuiContext context)
FocusState Tracks focusable widgets in submission order and moves focus with Tab or Shift+Tab. BeginFrame, Register, FocusedId
ImtuiInput Represents ordered key and character events for a single frame. ImtuiInput.FromConsoleKeyInfo, ImtuiInput.FromCharacter, ImtuiInput.FromKey
WidgetStateStorage Persists widget-local state by stable WidgetID. GetWidgetState<T>(id)

Input and focus

Input is supplied by the application at frame boundaries. This keeps the core library deterministic and avoids coupling reusable widget code to terminal reads. Console hosts can use the library-owned ImtuiInput.FromConsoleKeyInfo adapter, while tests can provide synthetic input directly. 

ConsoleKeyInfo key = Console.ReadKey(intercept: true);
ImtuiInput input = ImtuiInput.FromConsoleKeyInfo(key);

imtui.NewFrame(size, input);

Focus is based on stable widget IDs and submission order. At the start of a frame, focus navigation uses the previous frame's order. As widgets are submitted during the current frame, they register themselves again.

The model intentionally starts small: focusable widgets register themselves, Tab and Shift+Tab move focus, and Enter or Space activates the focused widget. More navigation rules can be added later without changing the public widget API.

Stateful widgets

ButtonWidget and CheckboxWidget only need frame-local behavior: resolve an ID, register focus, render, and return activation or changed state. TextFieldWidget also needs persistent state, so it stores a cursor index in WidgetStateStorage using its stable WidgetID. 

WidgetID id = context.GetId(Label);
bool focused = context.RegisterFocusable(id);
TextFieldState state = context.GetWidgetState<TextFieldState>(id);

bool changed = focused && ApplyInput(context, state, ref value);

The caller still owns the text value through ref string value. The widget owns editor details such as the cursor position. This matches immediate-mode expectations while allowing persistent internal behavior.

Testing strategy

The design was built with red-green TDD. Each layer has targeted tests: renderer validation, context text output, frame input, focus navigation, widget submission, and widget API behavior.

Deterministic frame size

Tests call NewFrame(new Size(...)) so they do not depend on the host terminal dimensions.

Synthetic input

Tests pass ImtuiInput directly instead of simulating terminal reads.

Internal visibility

The test assembly uses internals to verify focus, submission, and screen output without public debug hooks.

Current boundaries

This is intentionally a minimal first slice. The widget cursor advances one row per widget. Styling is limited to normal and focused states. There is no full layout engine, disabled state, mouse input, clipboard integration, or terminal driver abstraction yet.

Those features can be layered in later because the public API is separate from internal widget execution and because input, focus, rendering, and state now have clear seams.
